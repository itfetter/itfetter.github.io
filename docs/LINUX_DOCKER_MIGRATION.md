# 云服务器开发与部署指南

项目以云服务器上的 Docker 容器作为主要运行与联调环境，使用 Node.js + SQLite + 本地图片。源码统一由 GitHub 管理，镜像由 GitHub Actions 构建并发布到 GHCR，再通过 SSH 在服务器部署。Cloudflare Workers + D1 + R2 保留为兼容方案。

部署容器、导入内容和切换正式域名是独立步骤；当前实例和切换验收记录见 [项目交接](../PROJECT_HANDOFF.md)，不要仅凭文档架构推断公网入口已经切换。

## 镜像与数据

应用镜像为 `ghcr.io/itfetter/itfetter-blog`，优先使用通过测试的 `sha-完整提交号` 标签或镜像 digest。`latest` 仅用于查看最近版本，不建议作为生产实例的固定配置。基础运行环境是 Node.js 24，使用内置 SQLite，不需要另起数据库容器。仅支持单实例进程使用自己的本地数据库；不要共享 SQLite 文件给多个独立实例，也不要挂载到网络文件系统。

镜像只含公开程序、生产依赖和静态资源，不含文章、管理员密码、连接配置或数据库。数据库 `/data/blog.sqlite` 和图片 `/uploads` 必须绑定到主机持久化目录；SQLite 的 WAL/SHM 文件属于同一数据目录。容器重建不删除这些目录。数据库和图片分开备份，GitHub 代码历史不能代替数据备份。

## 宝塔多实例目录

沿用宝塔实际生成的“应用目录/实例目录”：

```text
/www/dk_project/dk_app/itfetter-blog/itfetter-blog-<实例标识>/
├── compose.yml
├── .env                 # 该实例的私有配置
├── data/                # SQLite 与迁移前快照
└── uploads/             # 图片原文件
```

不再额外套项目目录。每个实例使用独立端口、Compose 项目名及数据目录；示例未固定容器名。使用宝塔现有 Docker 引擎，在面板正式创建或导入编排，不手改 apps.json、apptags.json、installed.json；目录位置本身不保证编排自动登记。不要调整其他应用或 Docker data-root。

## 创建一个实例

1. 在宝塔创建实例后，将仓库 `deploy/compose.yml` 和 `deploy/.env.example` 分别放到实例目录的 `compose.yml` 和 `.env`。
2. 填入已验证镜像标签和独立 BLOG_PORT，无需设置或绑定 PUBLIC_ORIGIN。应用根据 Host 识别当前域名/IP及端口；域名与证书在宝塔管理，更换域名不必修改镜像或容器域名配置。
3. 在该实例目录创建 data、uploads，所有者设为容器运行用户 UID/GID 1000，权限建议 700，`.env` 权限 600。仅修改本实例路径，不递归改整个 dk_app。
4. 在宝塔启动编排；命令行管理时，在实例目录执行 `docker compose --env-file .env -f compose.yml -p <独立实例名> up -d`。后续始终用同一个项目名。检查容器健康状态和宝塔面板中的名称、端口、挂载。
5. 由宝塔 Nginx 为域名提供 HTTPS，参考 `deploy/nginx-location.conf.example` 代理到该实例的 `127.0.0.1:BLOG_PORT`。保留宝塔原证书与 HTTP 到 HTTPS 跳转。不要将容器端口直接暴露到公网。
6. 根据实际实例网络检查 Docker 网关（`docker network inspect <实例网络名>`），将主机代理在容器看来对应的精确 IP 填到 TRUST_PROXY_IPS。Nginx 必须覆盖 Host、X-Real-IP，并通过 `X-Forwarded-Proto $scheme` 告知外部协议，而不是透传访客提供的值。未配置可信代理时不信任转发头；多个访客可能共享代理限额，HTTPS代理后的登录也会因为只识别到HTTP而被拒绝。不要填通配符、整个网段或其他容器 IP。更改后重建本实例。
7. 首次账号创建优先使用网页：建立下文的 SSH 本地转发，在 `http://127.0.0.1:3100/admin/` 填写管理员账号、12–128字符密码及确认密码，创建后自动进入后台。仅限实际回环连接或已配置可信主机网关、无代理转发头的本地预览请求；公网域名/反代入口不能抢先创建账号。已有管理员时初始化永久关闭，正常显示登录页，不清空文章或图片。

命令行初始化保留作运维备用：`docker compose -p <独立实例名> exec blog node server/admin.mjs`，交互输入密码，不写入命令行、环境或镜像。重置已有账号必须显式使用 `--reset`，会撤销旧会话；不要与网页初始化同时运行。

健康检查为容器内部的 `/healthz`，验证进程和 SQLite 可读；它不代表文章已迁移或公网 HTTPS 已验收。使用临时 HTTPS 域名检查前后台，不要在验收前切换正式域名。

## 从 Cloudflare 迁移内容

先在原后台下载包含图片的 JSON 备份，并核对后台提示的备份范围与数量限制。新实例创建独立管理员，登录新后台，使用现有恢复入口导入。恢复是补缺，不覆盖同名已有内容；若数量超过后台备份上限，应另做完整 D1/R2 导出转换，不能直接将 D1 SQL 塞进已迁移的 SQLite 文件。

JSON 不包含管理员密码、会话或限速数据，管理员需单独初始化。图片恢复保持 `/images/<key>` 路径；外部引用仅保留链接，不会自动下载。核对文章、独立草稿、历史、合集、评论回复、私密留言、联系方式和图片，再决定迁移窗口。

最终切换时暂停旧站写入，做最终备份和补齐，验证新实例后再调整域名入口，避免两个后端分别接收新内容。保留旧站与备份作为回退依据。此步骤需要实际迁移验收，构建镜像不会自动执行。

## 更新、备份与回滚

GitHub Actions 执行原业务测试、容器适配测试和实际容器冒烟测试后发布 GHCR。主机拉取镜像可能需要网络连通性；部署前确认 GHCR Package 为 Public 并验证匿名拉取；仓库公开不代表包一定公开。

更新前：记录当前镜像 digest，在后台暂停写入，运行 `docker compose -p <独立实例名> exec blog node server/backup.mjs` 创建一致 SQLite 快照。将快照和 uploads 复制到实例目录外的独立备份位置；为了数据库和图片属于同一时间点，完整备份期间保持停止写入。不要仅复制正在写入的 blog.sqlite 而漏掉 WAL。

先检查 `compose.yml` 的 `image`：若使用 `${IMAGE_TAG}` 模板，则修改 `.env` 中的 IMAGE_TAG；若已固定 `@sha256:…`，则更新 Compose 中的镜像 digest，只改 IMAGE_TAG 不会生效。配置通过 `docker compose -p <独立实例名> config --quiet` 校验后，执行 `docker compose -p <独立实例名> pull blog`，再 `docker compose -p <独立实例名> up -d blog`。启动自动按顺序执行新增 SQL 迁移；升级前会在 data/backups 留一份 SQLite 快照。已经执行过的迁移校验和不能改变，迁移失败停止启动，不启动半升级应用。实例数据目录不可共用，升级和管理员初始化不要同时运行。

检查健康、日志、公开文章、登录、保存草稿、图片和评论。程序回滚使用旧镜像；如旧程序不兼容新数据库，必须在停止容器后用升级前快照与匹配的图片备份恢复，不能只切换镜像。禁止 `down -v`、删除 data/uploads，或执行会清除持久化数据的清理命令。定期将备份复制到服务器之外。

## 日常开发与云服务器联调

1. 在源码仓库修改界面、业务或适配代码。`worker/` 保留共享业务与 SQL 迁移，`server/` 提供 Node 运行适配；不要把“在云服务器开发”理解为直接修改容器内部文件。
2. 本机复用已有工具做轻量检查；不为测试自动安装依赖、Docker 或浏览器。依赖已具备时可执行 `node --test server/test.mjs`，缺失的完整环境交给云端 CI。
3. 提交 GitHub；`.github/workflows/container.yml` 运行原业务测试、Node 适配测试、真实 SQLite/HTTP 集成、镜像构建和实际容器验证，通过后发布 GHCR。Pull Request 只构建验证，不发布镜像。
4. 在独立云服务器测试实例拉取本次已通过检查的 SHA 标签或 digest，备份后重建应用容器；保持 data/uploads 挂载和实例项目名不变。
5. 通过 SSH 本地转发或测试域名，用真实浏览器检查首页、文章列表、搜索、文章阅读、图片和后台。静态文件/API 返回200不代表前端脚本已经成功执行，尤其要检查模块 MIME、控制台错误和列表实际渲染。测试写入只使用独立实例或明确的测试内容。
6. 验证完成后按既有正式实例的备份、更新流程发布。域名迁移另行核对 DNS、Nginx、证书、最终数据同步与入口访问，不自动切换旧站。

代码升级发布到镜像，日常文章和图片写入持久化数据。SQL 结构升级只新增迁移，不修改已应用迁移；运行中容器的临时文件修改不会作为下一版镜像的源码。

## SSH 本地预览

在**本机终端**使用已配置的 SSH 账号建立转发，例如：

```bash
ssh -N -T -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o ServerAliveCountMax=3 -L 127.0.0.1:3100:127.0.0.1:3100 -p <SSH端口> <SSH账号>@<服务器地址>
```

左侧 `127.0.0.1:3100` 是本机监听地址，右侧是服务器上的应用端口；如果本机3100被占用，可只将左侧改为其他空闲端口，并用相同端口访问浏览器。不要把服务器映射端口、本机转发端口与容器内部3000端口混为一谈。

连接成功后，打开 `http://127.0.0.1:3100/` 或 `http://localhost:3100/`。隧道必须保持运行；关闭SSH、电脑重启或连接断开后需要重新建立。后台启动时使用隐藏窗口并保留进程管理信息；不要创建开机服务或修改系统设置。已有隧道可复用，不重复占用同一端口。

本地HTTP地址自动使用仅限localhost/127.0.0.1的预览会话；公网域名下登录继续要求HTTPS。正式域名访问通过宝塔Nginx进入，不依赖这条本机SSH隧道。不要将应用端口或SSH监听转发绑定到公网，也不要把公网域名伪装为localhost作为正式部署方式。

容器不再校验固定域名；HTTP Host 仍进行语法和请求路径校验，同源检查比较当前请求Origin。只信任 TRUST_PROXY_IPS 中代理的 X-Forwarded-Proto，不采信 X-Forwarded-Host。宝塔应仅将所配置域名转发到本机端口，未知域名由Nginx默认站点处理。页面站点元信息、robots与sitemap跟随当前访问入口，文章正文里的作者原始链接不批量改写。
